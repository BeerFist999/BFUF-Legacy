# Архитектура BFUF-Legacy

## 1. Общая схема проекта

BFUF-Legacy — модульный аддон для World of Warcraft. Код построен вокруг глобальной таблицы `BFUF`, которую получает каждый Lua-модуль через стандартную инициализацию Blizzard:

```lua
local addonName, BFUF = ...
```

`Core/Init.lua` создаёт базовые пространства имён, а основной event frame запускает инициализацию после события `ADDON_LOADED` для аддона `BFUF-Legacy`. Последующая последовательность определена в `Core/Bootstrap.lua`.

```text
BFUF
├── Core       # Инициализация и системные модули
├── DB         # Пространство имён данных
├── Frames     # Unit frames
├── Elements   # Элементы фреймов
├── Options    # Настройки
└── Utils      # Вспомогательные функции
```

Файлы загружаются в порядке, заданном в `BFUF.toc`.

## 2. Назначение каталогов

| Каталог | Назначение |
| --- | --- |
| `Core/` | Ядро аддона: инициализация, база данных, события и локализация. |
| `Frames/` | Модули базовых unit frames. |
| `Elements/` | Визуальные и информационные элементы unit frames. |
| `Layouts/` | Шаблоны расположения и компоновки элементов интерфейса. |
| `Options/` | Модули пользовательских настроек аддона. |
| `Locale/` | Локализационные строки и языковые ресурсы. |
| `Media/` | Статические ресурсы: текстуры, шрифты и другие медиафайлы. |
| `Utils/` | Вспомогательные утилиты общего назначения. |
| `docs/` | Проектная и техническая документация. |

## 3. Ответственность модулей

### Core

- `Init.lua` — создаёт пространства имён `BFUF`, регистрирует `ADDON_LOADED` и запускает инициализацию.
- `Bootstrap.lua` — определяет последовательность будущей инициализации подсистем.
- `Database.lua` — зарезервирован для работы с базой данных.
- `Events.lua` — зарезервирован для регистрации и обработки событий.
- `Localization.lua` — зарезервирован для загрузки локализации.

### Frames

- `Player.lua` — фрейм игрока.
- `Target.lua` — фрейм цели.
- `TargetTarget.lua` — фрейм цели цели.
- `Boss.lua` — фреймы боссов.

### Elements

- `Health.lua` — элемент здоровья.
- `Power.lua` — элемент ресурса.
- `Portrait.lua` — портрет.
- `Castbar.lua` — полоса применения заклинаний.
- `Auras.lua` — ауры.
- `Text.lua` — текстовые элементы.

### Options и Utils

- `Options/Options.lua` — модуль настроек.
- `Utils/Helpers.lua` — вспомогательные функции.

Перечисленные модули, кроме `Init.lua` и `Bootstrap.lua`, пока являются каркасом без реализации.

## 4. Правила зависимостей между модулями

- Модули используют общую таблицу `BFUF` и её явно выделенные пространства имён.
- Зависимость направлена от ядра к прикладным модулям: `Core` подготавливает окружение, а `Frames`, `Elements`, `Options` и `Utils` используют его.
- `Frames` могут использовать элементы из `Elements`; элементы не должны напрямую зависеть от конкретных unit frames.
- `Layouts`, `Locale` и `Media` предоставляют ресурсы и описания, не управляя инициализацией ядра.
- Порядок загрузки Lua-файлов задаётся только `BFUF.toc`.
- Используется только API Blizzard; Ace3 и другие сторонние библиотеки не применяются.

## 5. Правила именования

- Один файл соответствует одному модулю и одной зоне ответственности.
- Имена каталогов, файлов и публичных сущностей должны отражать их назначение.
- Для Lua-переменных и функций применяется `camelCase`.
- Для констант применяется `UPPER_SNAKE_CASE`.
- Неясные сокращения не используются, кроме общепринятых терминов Blizzard API.
- Комментарии в исходном коде пишутся на русском языке.

## 6. Порядок инициализации

Порядок задаётся существующим `Core/Bootstrap.lua`:

```text
Init → Bootstrap → Database → Localization → Events → Frames → Elements
```

1. `Init` создаёт базовые пространства имён и ожидает `ADDON_LOADED`.
2. `Bootstrap` запускается после `BFUF:Initialize()` и определяет дальнейшие этапы.
3. Затем будут подключаться база данных, локализация и события.
4. После подготовки системных подсистем будут создаваться фреймы и их элементы.

На текущем этапе перечисленные будущие шаги представлены только комментариями и не содержат игровой логики.

## 7. Принципы модульной архитектуры

- Использовать только Blizzard API.
- Не использовать Ace3.
- Сохранять модули небольшими и изолированными.
- Явно определять взаимодействие между модулями.
- Не смешивать инициализацию, обработку событий и представление без необходимости.
- Документировать значимые архитектурные решения.
- Поддерживать совместимость с целевыми legacy-клиентами World of Warcraft.
